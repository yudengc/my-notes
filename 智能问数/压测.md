# 智能问数系统 JMeter 压测计划

## 1. 压测概述

### 1.1 压测目标
- 评估系统在高并发场景下的性能表现
- 识别系统性能瓶颈（响应时间、吞吐量、资源利用率）
- 验证系统在不同负载下的稳定性
- 为容量规划提供数据支撑

### 1.2 压测范围
本次压测覆盖系统所有核心API接口：

| 模块 | 接口路径 | HTTP方法 | 接口说明 |
|------|----------|----------|----------|
| SQL生成 | `/sql/llm` | POST | LLM SQL生成 |
| SQL生成 | `/sql/llm_messages` | POST | LLM消息生成 |
| SQL生成 | `/sql/func_implement_transfer` | POST | 函数实现转换 |
| 实体抽取 | `/entity_extract` | POST | 要素提取&定表 |
| 实体抽取 | `/health_check` | POST | 健康检查 |
| 实体召回 | `/entity_recall` | POST | ES召回 |
| 澄清模块 | `/clarify` | POST | 澄清生成 |
| 样例模块 | `/demo` | POST | 样例演示 |

### 1.3 压测环境

| 环境项 | 配置说明 |
|--------|----------|
| 服务器配置 | 待补充（CPU/内存/磁盘） |
| 部署方式 | Gunicorn + UvicornWorker (workers=1, threads=2) |
| 超时配置 | timeout=600s, keepalive=65s |
| 数据库 | PostgreSQL (asyncpg) |
| 缓存 | Redis |
| 外部依赖 | LLM服务、ES服务 |

## 2. 并发用户数设置

### 2.1 并发梯度设计

| 场景级别 | 并发用户数 | 持续时间 | 目的 |
|----------|------------|----------|------|
| 低负载 | 10 | 10分钟 | 验证基础功能正常 |
| 正常负载 | 50 | 20分钟 | 模拟日常使用场景 |
| 高负载 | 100 | 30分钟 | 验证系统处理能力上限 |
| 峰值负载 | 200 | 15分钟 | 验证系统极限承受能力 |
| 稳定性测试 | 50 | 2小时 | 验证长时间运行稳定性 |

### 2.2 JMeter线程组配置

```
线程组配置示例（以正常负载50并发为例）：
- 线程数（用户数）：50
- Ramp-Up时间：60秒（用户逐步加入，避免瞬时冲击）
- 循环次数：持续运行（勾选"永远"）
- 调度器：启用
  - 持续时间：1200秒（20分钟）
  - 启动延迟：0秒
```

### 2.3 并发策略说明
- **Ramp-Up设置**：建议设置为并发数的1-2倍秒数，如50并发设置Ramp-Up=60s，即每秒新增约1个用户
- **稳态运行**：排除Ramp-Up和下降阶段，取中间80%时间段的数据作为有效压测数据
- **多模块混合**：根据实际业务比例分配各接口并发权重

## 3. 性能指标定义

### 3.1 核心性能指标

| 指标名称 | 指标说明 | 达标标准 | 严重阈值 |
|----------|----------|----------|----------|
| 平均响应时间（ART） | 请求从发送到收到完整响应的平均时间 | ≤2秒 | >5秒 |
| 90%响应时间（RT90） | 90%的请求在此时间内完成 | ≤3秒 | >8秒 |
| 95%响应时间（RT95） | 95%的请求在此时间内完成 | ≤4秒 | >10秒 |
| 99%响应时间（RT99） | 99%的请求在此时间内完成 | ≤6秒 | >15秒 |
| 吞吐量（TPS/QPS） | 每秒处理的请求数 | ≥10 TPS | <5 TPS |
| 错误率 | 失败请求占总请求的比例 | ≤0.1% | >1% |
| 并发用户数 | 同时在线执行操作的用户数 | 按场景设定 | - |

### 3.2 资源监控指标

| 资源类型 | 监控指标 | 达标标准 | 严重阈值 |
|----------|----------|----------|----------|
| CPU | CPU使用率 | ≤70% | >90% |
| 内存 | 内存使用率 | ≤80% | >90% |
| 磁盘 | 磁盘I/O等待 | ≤30% | >60% |
| 网络 | 网络带宽使用率 | ≤70% | >90% |

### 3.3 业务指标

| 指标名称 | 指标说明 | 达标标准 |
|----------|----------|----------|
| SQL生成成功率 | /sql/llm 接口返回有效SQL的比例 | ≥95% |
| 实体抽取准确率 | /entity_extract 接口正确抽取实体的比例 | ≥90% |
| 召回覆盖率 | /entity_recall 接口返回候选集的比例 | ≥85% |

## 4. 压测场景设计

### 4.1 单接口压测场景

#### 场景1：SQL生成接口压测
- **接口**：`POST /sql/llm`
- **目的**：验证LLM SQL生成接口在高并发下的性能
- **并发数**：10/50/100/200
- **持续时间**：20分钟/场景
- **关注指标**：响应时间（LLM调用通常较慢）、错误率、LLM服务超时情况

#### 场景2：实体抽取接口压测
- **接口**：`POST /entity_extract`
- **目的**：验证实体抽取和表选择性能
- **并发数**：10/50/100/200
- **持续时间**：20分钟/场景
- **关注指标**：响应时间、并发冲突、ES查询性能

#### 场景3：实体召回接口压测
- **接口**：`POST /entity_recall`
- **目的**：验证ES混合检索召回性能
- **并发数**：50/100/200
- **持续时间**：20分钟/场景
- **关注指标**：ES响应时间、召回准确率、连接池耗尽情况

#### 场景4：澄清接口压测
- **接口**：`POST /clarify`
- **目的**：验证澄清生成性能
- **并发数**：50/100/200
- **持续时间**：20分钟/场景

#### 场景5：样例接口压测
- **接口**：`POST /demo`
- **目的**：验证样例演示功能性能
- **并发数**：50/100/200
- **持续时间**：20分钟/场景

### 4.2 混合场景压测

#### 场景6：典型用户行为混合压测
模拟真实用户问数流程：

| 步骤 | 接口 | 占比 | 说明 |
|------|------|------|------|
| 1 | `/entity_recall` | 30% | 实体召回 |

### 4.3 特殊场景

#### 场景8：突增流量测试
- **目的**：验证系统在突发流量下的弹性能力

## 5. 压测数据准备

### 5.1 认证数据

系统使用 token 认证（sgov 网关），需要准备：

```
请求头配置：
- Authorization: Bearer <your_token>
- x-tracerid: <unique_trace_id>  (可选，用于链路追踪)
- Content-Type: application/json
```

**JMeter配置**：
- 在HTTP请求默认值中设置通用请求头
- 或使用HTTP信息头管理器配置

### 5.2 请求参数模板

#### 5.2.1 SQL生成接口 `/sql/llm`

```json
{
  "tenant_id": ${tenant_id},
  "question": "${question}",
  "sc_result": {
    "scene_name": "示例场景",
    "scene_id": "scene_001"
  },
  "env_status": "prod",
  "stop": ["<reason"],
  "quest_source": 1,
  "question_type": "查数值"
}
```

**参数化变量**：
- `tenant_id`：租户ID，从CSV文件读取
- `question`：用户问题，准备50-100条典型问数语句

**问题语料示例**：
```
2024年Q1的营业收入是多少？
各部门的利润排名？
华东地区上个月的销售额？
产品A的库存数量？
今年累计的合同金额？
```

#### 5.2.2 实体抽取接口 `/entity_extract`

```json
{
  "question": "${question}",
  "tenant_id": ${tenant_id},
  "user_account": "${user_account}",
  "question_type": "查数值",
  "responsibility_center": "all",
  "user_currency": "CNY",
  "env_status": "prod",
  "caliber_source": "intent_caliber",
  "data_caliber": {},
  "model_field_clarify": {}
}
```

**参数化变量**：
- `user_account`：用户账号，准备10-20个不同账号
- `question`：同SQL生成接口
- `question_type`：从["查信息", "查数值", "查排名"]中随机选取

#### 5.2.3 实体召回接口 `/entity_recall`

```json
{
  "query": "${question}",
  "tenant_id": ${tenant_id},
  "env_status": "prod",
  "top_k": 10,
  "rescore_window": 100,

  "text_boost": 1.0
}
```

#### 5.2.4 澄清接口 `/clarify`

    {
      "entity_name": "营业收入",

│   └── 监听器集合

- **协议**：`http`

## 7. 压测执行步骤

### 7.1 压测前准备

1. **环境检查**
   ```bash
   # 确认服务状态
   curl http://<server_ip>/fin_ida_algorithm/test
   
   # 确认依赖服务状态
   curl http://<es_server>:9200/_cluster/health
   ```

2. **数据准备**
   - 准备CSV参数文件（至少50条问题语料）
   - 获取有效的认证Token
   - 确认测试数据已初始化

3. **监控准备**
   - 启动服务器监控（CPU、内存、磁盘IO）
   - 启动数据库监控
   - 启动ES监控
   - 启动JVM监控（如有）

4. **JMeter配置优化**
   - 调整JMeter堆内存：修改 `jmeter.bat` 或 `jmeter.sh`
     ```
     HEAP="-Xms2g -Xmx4g"
     ```
   - 禁用不必要的监听器（压测时只保留聚合报告）
   - 设置合理的日志级别

### 7.2 压测执行顺序

```
第1步：单接口基准测试（低负载）
  └── 10并发，验证接口功能正常，记录基准响应时间

第2步：单接口梯度压测
  ├── 50并发，记录性能数据
  ├── 100并发，记录性能数据
  └── 200并发，记录性能数据

第3步：混合场景压测
  ├── 50并发混合场景，20分钟
  └── 100并发混合场景，20分钟

第4步：稳定性测试
  └── 50并发，持续2小时

第5步：突增流量测试
  └── 10并发 → 100并发 → 10并发
```

### 7.3 命令行执行方式

```bash
# 非GUI模式执行测试（推荐）
jmeter -n -t "智能问数压测计划.jmx" -l results/result_50threads.jtl -e -o results/html_report_50threads

# 参数说明：
# -n：非GUI模式
# -t：测试计划文件
# -l：结果文件
# -e：测试结束后生成HTML报告
# -o：HTML报告输出目录

# 带参数执行
jmeter -n -t "智能问数压测计划.jmx" \
  -JBASE_URL=http://10.0.0.100:80 \
  -JAUTH_TOKEN=your_token_here \
  -l results/result.jtl -e -o results/html_report
```

## 9. 注意事项

### 9.1 JMeter配置优化

1. **JVM调优**
   ```
   修改 bin/jmeter 或 bin/jmeter.bat:
   HEAP="-Xms2g -Xmx4g"
   NEW="-XX:NewSize=1g -XX:MaxNewSize=1g"
   SURVIVOR="-XX:SurvivorRatio=8 -XX:TargetSurvivorRatio=90"
   TENURING="-XX:MaxTenuringThreshold=2"
   ```

2. **JMeter属性优化**
   ```
   修改 bin/jmeter.properties:
   httpclient4.time_to_live=60000
   httpclient4.retrycount=3
   ```

3. **监听器优化**
   - 压测时禁用"查看结果树"监听器
   - 仅保留"聚合报告"和必要的图形监听器
   - 使用 `-l` 参数记录结果，避免内存占用

### 9.2 压测注意事项

1. **网络环境**
   - 确保压测机与服务器网络延迟稳定
   - 建议使用局域网进行压测，避免网络带宽成为瓶颈
   - 压测机性能需足够，避免压测机成为瓶颈

2. **数据隔离**
   - 压测数据与生产数据隔离
   - 压测前备份重要数据
   - 压测后清理测试数据

3. **依赖服务**
   - 确认LLM服务的压测容量，避免外部服务成为瓶颈
   - 确认ES服务的压测容量
   - 确认数据库连接池配置

4. **安全考虑**
   - 压测前通知相关团队
   - 避免在业务高峰期进行压测
   - 准备应急预案，压测异常时能快速恢复

### 9.3 常见问题排查

| 问题 | 可能原因 | 解决方案 |
|------|----------|----------|
| 响应时间过长 | LLM服务响应慢 | 检查LLM服务状态，增加超时时间 |
| 连接拒绝 | 服务器连接数耗尽 | 调整Gunicorn配置，增加workers/threads |
| 502/504错误 | 上游服务超时 | 检查Nginx/gunicorn超时配置 |
| 内存溢出 | 内存泄漏或配置不足 | 检查代码，增加服务器内存 |
| TPS上不去 | 数据库/ES瓶颈 | 检查数据库连接池、慢查询 |

## 附录A：JMeter快速入门

### A.1 安装JMeter
1. 下载JMeter：https://jmeter.apache.org/download_jmeter.cgi
2. 解压到本地目录
3. 配置环境变量（可选）
4. 运行 `bin/jmeter.bat` (Windows) 或 `bin/jmeter` (Linux/Mac)

### A.2 创建测试计划
1. 打开JMeter
2. 右键"测试计划" → 添加 → 线程组
3. 配置线程数、Ramp-Up、循环次数
4. 右键线程组 → 添加 → Sampler → HTTP请求
5. 配置请求参数
6. 右键线程组 → 添加 → 监听器 → 聚合报告
7. 保存测试计划

### A.3 运行测试
1. GUI模式：点击工具栏"启动"按钮
2. 非GUI模式：使用命令行执行（推荐）
